La capa de caché de [Laravel](https://laravel.com/) es una de las partes más elegantes del framework. Una sola llamada a `Cache::remember()` y de repente tu endpoint va como un cohete, la base de datos puede respirar y tus usuarios dejan de quejarse. Simple, efectivo y engañosamente fácil de malutilizar.

Antes de envolver todo en un `Cache::remember()`, hay algunas cosas que conviene conocer. En este post repaso consejos prácticos usando un ejemplo concreto: cachear los equipos a los que pertenece un usuario.

## El punto de partida

Imagina que tienes un método en un controlador que devuelve los equipos del usuario autenticado:

```php
public function getTeams(#[CurrentUser] User $user): Collection
{
    return $user->teams()->get();
}
```

Los equipos no cambian muy a menudo, pero este endpoint puede llamarse en cada carga de página de una SPA. Añadir una caché es un beneficio evidente:

```php
public function getTeams(#[CurrentUser] User $user): Collection
{
    return Cache::remember(
        'user:' . $user->id . ':teams',
        3600,
        fn () => $user->teams()->get()
    );
}
```

Funciona. Pero podemos hacerlo mejor.

## Consejo 1: evita cachear colecciones de Eloquent

No hay nada técnicamente incorrecto en cachear una colección o un modelo de [Eloquent](https://laravel.com/docs/eloquent) — es a menudo el camino más fácil. El problema es que serializar objetos completos de Eloquent es costoso. El tamaño serializado de una colección puede ser varios órdenes de magnitud mayor que los datos en bruto que representa, especialmente si se han cargado relaciones o los modelos tienen muchos campos ocultos.

En la práctica, serializar y deserializar una colección de Eloquent cacheada puede acabar siendo más lento que ir directamente a la base de datos, anulando el propósito. Lo recomendable es cachear arrays simples:

```php
public function getTeams(#[CurrentUser] User $user): array
{
    return Cache::remember(
        'user:' . $user->id . ':teams',
        3600,
        fn () => $user->teams()->get(['id', 'name'])->toArray()
    );
}
```

Seleccionar solo las columnas que realmente necesitas (`['id', 'name']`) mantiene el payload pequeño y la caché liviana.

## Consejo 2: cachea el JSON directamente

Si tu endpoint devuelve una respuesta JSON, puedes ir un paso más allá. En lugar de almacenar un array y dejar que Laravel lo serialice a JSON en cada petición, guarda el string JSON directamente y devuélvelo con `JsonResponse::fromJsonString()`:

```php
public function getTeams(#[CurrentUser] User $user): JsonResponse
{
    return JsonResponse::fromJsonString(
        Cache::remember(
            'user:' . $user->id . ':teams',
            3600,
            fn () => json_encode($user->teams()->get(['id', 'name']), JSON_THROW_ON_ERROR)
        )
    );
}
```

Esto elimina por completo el ciclo de serializar → deserializar → volver a serializar. En un caché hit, el camino es: leer un string de [Redis](https://redis.io/), envolverlo en una respuesta. Nada más.

## Consejo 3: usa tags de caché para la invalidación

Los ejemplos anteriores tienen un problema: ¿cómo invalidas la caché cuando los equipos cambian? Confiar únicamente en la expiración por TTL rara vez es suficiente. Los [tags de caché de Laravel](https://laravel.com/docs/12.x/cache#cache-tags) te permiten agrupar entradas de caché relacionadas y vaciarlas todas de una vez.

> **Requisito de driver**: los tags de caché solo están disponibles con los drivers `redis` y `memcached`. No funcionan con los drivers `file` o `database` (el driver por defecto en Laravel).

```php
public function getTeams(#[CurrentUser] User $user): JsonResponse
{
    return JsonResponse::fromJsonString(
        Cache::tags(['org:' . $user->organization_id . ':teams'])
            ->remember(
                'user:' . $user->id . ':teams',
                3600,
                fn () => json_encode($user->teams()->get(['id', 'name']), JSON_THROW_ON_ERROR)
            )
    );
}

public function saveTeam(Request $request, Team $team): JsonResponse
{
    // Guardar el equipo...

    Cache::tags(['org:' . $team->organization_id . ':teams'])->flush();

    return response()->json(['success' => true]);
}
```

Al usar el tag `org:{id}:teams`, un solo flush tras actualizar un equipo invalida la lista de todos los usuarios de esa organización de golpe.

### Una nota sobre el rendimiento de los tags en Redis

La implementación de tags en Redis de Laravel usa sets para rastrear qué claves pertenecen a cada tag. Con un número grande de elementos cacheados, esto puede suponer hasta dos llamadas de red adicionales a Redis por cada ~1000 entradas del tag set. Puedes revisar la implementación en [`RedisTagSet`](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Cache/RedisTagSet.php) y [`RedisTaggedCache`](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Cache/RedisTaggedCache.php). En la mayoría de aplicaciones esto es despreciable, pero vale la pena tenerlo en mente si operas a gran escala.

## Costes ocultos que debes evaluar

Añadir caché no es gratis. Antes de adoptar una estrategia de caching, considera lo siguiente:

**Latencia en caché miss.** La primera petición tras un caché miss (o tras arrancar la aplicación) golpea la base de datos, más el tiempo de serialización para poblar la caché. Para queries lentas, esto significa que algunas peticiones serán notablemente más lentas que otras. Asegúrate de que tu latencia p99 es aceptable, no solo el promedio.

**Punto de fallo adicional.** ¿Qué ocurre si tu almacén de caché cae? ¿Tu aplicación vuelve a la base de datos de forma controlada, o revienta? Asegúrate de que el comportamiento de fallback es intencional y está probado.

**Incoherencias en los deploys.** Si cambias la estructura de los datos cacheados en un deploy, puedes servir datos obsoletos con la estructura antigua hasta que expire la caché. Con deploys en rolling release, esta ventana puede durar varios minutos. Las opciones incluyen rotar el prefijo de la clave de caché en cada release, añadir un prefijo de versión, o gestionarlo manualmente en tu proceso de deploy.

## Prueba tu caché como es debido

Los bugs de caché son escurridizos porque a menudo solo aparecen bajo condiciones de timing específicas. Al escribir tests, asegúrate de cubrir:

- El camino de **caché miss**: la primera llamada golpea la base de datos y popula la caché.
- El camino de **caché hit**: las llamadas posteriores devuelven los datos cacheados y no tocan la base de datos.
- El camino de **invalidación**: tras la mutación correspondiente, la caché se vacía realmente y la siguiente llamada obtiene datos frescos.

Probar el ciclo completo de invalidación es donde se esconden la mayoría de los bugs de caché.

Además, ten mucho cuidado al usar datos cacheados para disparar efectos secundarios. Si tu código lee de la caché y luego envía un email, cobra una tarjeta o despacha un job basándose en esos datos, una caché obsoleta puede causar problemas reales. En caso de duda, obtén datos frescos para operaciones con efectos secundarios.
