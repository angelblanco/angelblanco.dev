[Laravel](https://laravel.com/)'s cache layer is one of the most elegant parts of the framework. A single `Cache::remember()` call and suddenly your endpoint is faster, your database can breathe, and your users stop complaining. Simple, effective, and deceptively easy to misuse.

Before you wrap everything in a `Cache::remember()`, there are a few things worth knowing. This post walks through practical tips using a concrete example: caching the teams a user belongs to.

## The starting point

Imagine you have a controller method that returns the teams for the authenticated user. User teams are constrained to a maximum of 50, so returning all of them without pagination seems reasonable.

```php
public function getTeams(#[CurrentUser] User $user): Collection
{
    return $user->teams()->get();
}
```

Teams don't change very often, but they are probably going to be use really often for access control. Adding a cache is an obvious win:

```php
public function getTeams(#[CurrentUser] User $user): Collection
{
    return Cache::remember(
        'user:' . $user->id . ':teams',
        3600,
        fn () => $user->teams()->get()
    );
}
```

This works. But we can do better.

## Tip 1: Avoid caching Eloquent collections if aiming for speed

There's nothing technically wrong with caching an [Eloquent](https://laravel.com/docs/eloquent) collection or model — it's often the easiest path. The problem is that serializing full Eloquent objects is expensive. The serialized size of a collection can be orders of magnitude larger than the raw data it represents, especially if relations are loaded or the models carry a lot of hidden fields.

In practice, if the cache hit ratio is low, serializing and deserializing a cached Eloquent collection can end up being slower than just hitting the database

Prefer caching plain arrays instead:

```php
public function getTeams(#[CurrentUser] User $user): array
{
    return Cache::remember(
        'user:' . $user->id . ':teams',
        3600,
        fn () => $user->teams()->get(['id', 'name'])->toArray()
    );
}
```

Selecting only the columns you actually need (`['id', 'name']`) keeps the payload small and the cache lean.

## Tip 2: If you are caching a JSON request, cache the json string directly

If your endpoint returns a JSON response, you can go one step further. Instead of storing an array and letting Laravel serialize it to JSON on every request, store the JSON string and return it directly using `JsonResponse::fromJsonString()`:

```php
public function getTeams(#[CurrentUser] User $user): JsonResponse
{
    return JsonResponse::fromJsonString(
        Cache::remember(
            'user:' . $user->id . ':teams',
            3600,
            fn () => json_encode($user->teams()->get(['id', 'name']), JSON_THROW_ON_ERROR)
        )
    );
}
```

This skips the serialize → deserialize → re-serialize cycle entirely. The cache hit path becomes: read a string from [Redis](https://redis.io/), wrap it in a response. That's it.

## Tip 3: Use cache tags for invalidation

The examples above have a problem: how do you invalidate the cache when teams change? Relying on TTL expiry alone is rarely enough. [Laravel cache tags](https://laravel.com/docs/12.x/cache#cache-tags) let you group related cache entries and flush them all at once.

> **Driver requirement**: cache tags are only supported by the `redis` and `memcached` drivers. They won't work with the `file` or `database` drivers (the default in a fresh Laravel install).

```php
public function getTeams(#[CurrentUser] User $user): JsonResponse
{
    return JsonResponse::fromJsonString(
        Cache::tags(['org:' . $user->organization_id . ':teams'])
            ->remember(
                'user:' . $user->id . ':teams',
                3600,
                fn () => json_encode($user->teams()->get(['id', 'name']), JSON_THROW_ON_ERROR)
            )
    );
}

public function saveTeam(Request $request, Team $team): JsonResponse
{
    // Save the team...

    Cache::tags(['org:' . $team->organization_id . ':teams'])->flush();

    return response()->json(['success' => true]);
}
```

By tagging all team caches under `org:{id}:teams`, flushing after a team update invalidates every user's team list within that organization in a single call.

### A note on Redis tag performance

Laravel's Redis tag implementation uses sets to track which keys belong to each tag. For large numbers of cached items, this can add up to two additional Redis network calls per ~1000 entries in the tag set. You can check the implementation in [`RedisTagSet`](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Cache/RedisTagSet.php) and [`RedisTaggedCache`](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Cache/RedisTaggedCache.php). For most applications this is negligible, but it's worth keeping in mind if you're operating at scale.

## Hidden costs worth evaluating

Adding cache isn't free. Before committing to a caching strategy, consider these:

**Cache miss latency.** The first request after a cache miss (or after startup) hits the database, plus the serialization overhead to populate the cache. For slow queries, this means some requests will be noticeably slower than others. Make sure your p99 latency is acceptable, not just your average.

**Extra point of failure.** What happens if your cache store goes down? Does your application fall back to the database gracefully, or does it crash? Make sure your fallback behavior is intentional and tested.

**Deploy incoherencies.** If you change the shape of cached data in a deploy, you might serve stale data with the old structure until the cache expires. With rolling deployments, this window can last several minutes. Options include rotating your cache key prefix with each release, adding a version prefix, or handling it manually in your deploy process.

## Test your cache properly

Cache bugs are sneaky because they often only surface under specific timing conditions. When writing tests, make sure to cover:

- The **cache miss** path: first call hits the database and populates the cache.
- The **cache hit** path: subsequent calls return cached data and skip the database.
- The **invalidation** path: after the relevant mutation, the cache is actually flushed and the next call fetches fresh data.

Testing the full invalidation cycle is where most cache bugs hide.

Also, be careful when using cached data to trigger side effects. If your code reads from cache and then sends an email, charges a card, or dispatches a job based on that data, stale cache can cause real problems. When in doubt, re-fetch fresh data for operations with side effects.
